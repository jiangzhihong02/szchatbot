# 数据获取与抓取说明（Scraping Notes）

本文件说明「深圳旅游助手」在**优惠 / 攻略数据**上的获取边界：默认不抓取第三方平台，以及为什么不抓、换成什么。

## 底线

默认**不抓取**小红书、大众点评、美团、抖音等第三方平台。优惠数据来自**人工精选种子**（`src/lib/data/deals.ts`），经可插拔的 `DataSource` 接口（`src/lib/sources/index.ts`）暴露。

**对独立开发者，不存在现实的合法 API 路径去读任意 UGC。** 真正开着的是这几条，按可行性排序：

| | 渠道 | 能拿到什么 | 门槛 |
|---|---|---|---|
| 1 | **高德／百度 POI** | 地点搜索、**评分、人均、类别、营业时间** | 自助、便宜（约 ¥30/万次，个人有免费额度）。**不是 UGC，没有评论正文** |
| 2 | 景区／文旅局／官方媒体的公众号、小程序 | 攻略、资讯 | 需官方**转载授权** |
| 3 | **直接向创作者取得授权** | 内容 | 小红书自己的蒲公英／合作广场就是这套合法模型；逐条谈 |
| 4 | 抖音生活服务／美团 ISV | | 企业认证 + 约 ¥10 万保证金 |
| 5 | 新榜 API | 趋势／话题信号 | 真 API，但小红书内容薄 |

**第 1 条是本项目唯一可以直接用的**——而且 key、签名、adapter 都已经接好。

## 为什么不能抓

1. **违反平台协议**。小红书、抖音、大众点评的用户协议**明文**禁止：小红书禁「非法抓取／盗链／模拟下载」及未经书面许可读取平台数据；抖音 §5.3(4) 禁「爬虫抓取、模拟下载、深度链接」，§5.3(7) 禁「任何形式的销售和商业使用，或向第三方提供」。

2. **法律已经不是「灰区」，是明文**。2025 年修订的《反不正当竞争法》**2025-10-15 生效**，新增**第 13 条第 3 款**：不得**避开或破坏技术管理措施**获取、使用他人合法持有的数据。此前只是判例法理，现在是条款。

3. **判例一致，且都在平台方，金额在涨**：

   | 案子 | 判赔 | 原则 |
   |---|---|---|
   | 大众点评 诉 百度 | ¥323 万 | 全文使用 8.6 万条评论构成「实质性替代」 |
   | 微博 诉 脉脉 | ¥200 万 | **三重授权**原则 |
   | 抖音 诉 刷宝 | ¥500 万 | 抓取 5 万条视频 |
   | 百度百科 诉 抖音百科 | ¥800 万 | |
   | 小红书 诉 厦门某公司 | **¥490 万** | **绕过反爬措施** |

   《个人信息保护法》第 27 条只允许在「合理范围内」处理**已公开**个人信息，**商业用途极可能超出**；绕过验证码／加密本身违法，与 robots.txt 无关。

4. **「官方开放平台」也不通向 UGC**。三个平台都有开放平台，但定位是**让你管自己的内容**：

   - **小红书**：文档化的权限是店铺／商品／订单／售后（商家）、笔记发布／数据报表（品牌、MCN）。笔记**搜索**权限未能证实会被授予。
   - **抖音**：`video.list` 只返回**已授权给你**的账号的视频；视频搜索是单独审批的特权。
   - **大众点评**：**北极星平台已于 2025-06-25 下线**，并入美团技术服务合作中心，只有 ISV／自研品牌商两种角色，**没有「普通读取方」**；只能读**你自己门店**的评论。

5. **第三方数据商大多是 dashboard，不是 API**。蝉妈妈、飞瓜、千瓜都没有公开 API（蝉妈妈自述为「公开渠道采集后统计分析」）。唯一真正有 API 的是**新榜**，但强在微信公众号，小红书内容很薄。那些直接卖「小红书 API」的，靠的是破解 `x-s` 签名 + 登录 cookie——**正是小红书诉厦门某公司判赔 490 万的那件事**。

6. **技术上不稳定**。登录态、签名、风控随时变化，维护成本高、易失效。

7. **而且它不适合我们的卡片**（这条与法律无关）。卡片是**可比较的结构**（区域／类别／必试／人均），UGC 是**散文**；从散文里抽字段，**抽错了不会报错，只会静静显示**。加上付费探店是结构性污染，接进「推荐卡」等于**把广告洗成推荐**。详见 [ADR-0001](adr/0001-deterministic-rules-over-llm.md) 划的那条线。

## 要接自动来源时怎么做

`DataSource` 接口就是为此预留的插座：

```ts
export interface DataSource {
  name: string;
  fetchDeals(): Promise<DealData[]>;
}
```

实现一个 `DataSource` 后推进 `SOURCES` 数组即可，上层 `fetchAllDeals()` 无需改动。

## 关于「实时」——分界是**变化速度**

| | 例子 | 做法 | 变化 |
|---|---|---|---|
| 变化快 | 天气、通关排队 | **运行时实时取**（有稳定接口） | 分钟级 |
| 变化慢 | 时间表、票价、优惠活动 | **静态种子 + 人手复核** | 周／月级 |
| 变化慢、但没人盯 | 口岸开放时间 | **变更监看**（见下） | 周／月级 |

变化越快越值得实时取；变化越慢，自动化的收益越小，而「抓错」的风险一点没少。

**已实现的半自动形态**：`.github/workflows/watch-borders.yml` —— 每日抓入境处管制站页面，变了就开 PR 让人过目。它**不解析时刻、不改 `borders.ts`**，因为官方页做不到可靠解析（深圳湾一段里有两时刻、时刻是自由散文）。**它不产出数据，只产出「变了」**，所以不可能产出错数据。详见 [README](../README.md) 的「資料從哪來」与票 13。
